# COCCHi比較・今後の改善計画（Phase 2B以降・設計のみ）

作成日：2026年8月19日

**このドキュメントは設計・計画のみです。ここに書かれている機能は一切実装していません。外部APIも何も登録・契約していません。**

---

## 0. 前提と注意

- Pioneer「COCCHi」など市販カーナビアプリの**画像・アイコン・ロゴ・文言・具体的な画面デザインはコピーしていません**。参考にしたのは「情報の優先順位のつけ方」「操作性」「機能の構成（何を、いつ、どの画面で見せるか）」という一般的な考え方のみです。Phase 2Aで作った方向アイコン（`js/ui/maneuverIcon.js`）は単純な線と矢印だけで自作しています。
- 以下の比較は、一般的な市販カーナビアプリが持つ機能カテゴリと、じぶんNaviベースの現状を突き合わせたものです。COCCHiの内部実装や非公開の仕様を調査したものではありません。
- **SmartLane（次の次の曲がり角まで考えた車線案内）は本アプリの核であり、以下のどの改善案も、SmartLaneの安全原則8項目（`CLAUDE.md`参照）を弱める方向には進めません。**

## 2. Phase 2B（次点候補・設計のみ）

### 2-1 ハイウェイモード（JCT/IC特化案内）

高速道路のJCT・IC付近で、通常より早いタイミング・専用の言い回しで案内する。

- **必要なAPI**：追加のAPIは不要。既存のDirections APIレスポンス（`step.type`が`'on ramp'`/`'off ramp'`、`roadClass`が`motorway`）を使って`js/core/voiceDecision.js`のしきい値を道路種別別に分岐させる形で実現できる見込み。
- **費用**：¥0（追加APIコールなし）
- **制限**：既存のDirections API呼び出し回数の範囲内。
- **プライバシー**：影響なし（既存データの使い方を変えるだけ）。
- **リスク**：SmartLaneのJCT分岐ロジック（`01_SmartLane仕様.md`のケース9等）との整合を取る必要がある。安全原則を弱めない設計が必須。

### 2-2 渋滞情報の反映

- **必要なAPI**：Mapbox Directions APIの`driving-traffic`プロファイル（現在は`driving`を使用）。
- **費用**：Mapboxの無料枠内には収まる想定だが、`driving-traffic`は`driving`よりリクエスト単価が高い場合がある。**登録前に最新の料金ページ（mapbox.com/pricing）で必ず確認すること。**
- **制限**：無料枠を超えると課金が発生する。現行の「ナビ開始時＋逸脱時（最短10秒間隔）」の呼び出し回数ルールは維持する。
- **プライバシー**：影響なし（経路データのみ）。

### 2-3 お気に入り・履歴・経由地

- **必要なAPI**：不要。`localStorage`に保存するだけで実現可能（走行ログと同じ方式）。
- **費用**：¥0
- **制限**：なし
- **プライバシー**：目的地の履歴は個人の行動範囲を示す情報のため、**端末内保存のみとし、外部送信しない設計**にすること（既存の走行ログと同じ方針）。

## 3. Phase 2C（要調査・設計のみ）

### 3-1 オフライン地図・オフラインナビ

- **必要なAPI**：Mapboxのオフライン地図機能は**モバイルSDK（iOS/Android native SDK）向けであり、Web（GL JS）版には無い**。Web版でオフライン対応するには、タイルを自前でキャッシュする実装が必要になり、Mapboxの利用規約上の制約（タイルの再配布・保存に関する条項）を確認しないと着手できない。
- **費用**：現時点で試算不可（SDK移行が前提になる可能性が高い＝実質Phase 3の範囲）。
- **制限**：不明（要調査）。
- **プライバシー**：影響小さい。
- **結論**：README.mdに記載の通り、意図的に見送っている機能。Web版のままでは中途半端な「なんちゃってオフライン」になり誤解を招くため、着手するならPhase 3（ネイティブ化）とセットで再検討する。

### 3-2 より自然な音声合成（VOICEVOX等）

- 詳細は既存の `docs/03_VOICEVOXナビ音声仕様（将来フェーズ）.md` を参照。
- 前回調査の結論：VOICEVOX公式エンジンはローカルサーバーが前提でWebアプリ単体では動かせない。非公式WASM版は実行速度・安定性の面で走行中のリアルタイム案内には不向きと判断し、**現時点ではOS標準音声のままとする**ことを既に決定済み。
- **必要なAPI/費用**：VOICEVOX公式エンジンをどこかのサーバーで常時起動する場合、サーバー代（月額数百〜数千円規模）が発生する。無料の範囲で完結させたいという方針とは相性が悪い。
- 再検討する場合は、着手前に必ず「Webアプリのまま実現できるか、ネイティブ化が必要か」を再調査すること（`docs/03`の既存の指示のまま）。

### 3-3 天気連携

- **必要なAPI候補**：Open-Meteo（APIキー不要・無料、商用利用も無料枠あり）が個人利用には最有力。OpenWeatherMap等は無料枠はあるがAPIキー登録が必要。
- **費用**：Open-Meteoなら¥0（利用規約の範囲内）。
- **制限**：Open-Meteoは無料利用時にリクエスト数の緩やかな制限がある（要最新の利用規約確認）。
- **プライバシー**：目的地の緯度経度を天気APIに送信することになるため、送信先が信頼できるか・送信するのは目的地座標のみで個人を特定する情報を含まないかを確認すること。

## 4. Phase 2D（要法的・倫理的確認・設計のみ）

### 4-1 オービス・取締り情報の表示

- 市販カーナビでは一般的な機能だが、情報源（データの正確性・更新頻度・提供元のライセンス）の精査が必要。
- **必要なAPI**：無料で信頼できる日本国内のオービス座標データソースは調査未着手。個人が作成したデータセットを使う場合、正確性の保証が無く、誤った案内や法的トラブルにつながるリスクがある。
- **費用**：データソースにより異なる（要調査）。
- **プライバシー**：影響小さい。
- **結論**：**着手前に必ずデータソースの信頼性と利用規約を確認すること。** 安全原則8項目と同様、「不確かな情報は出さない」を優先する。

## 5. Phase 3（ネイティブ化・設計のみ）

### 5-1 Android AIBOX向けネイティブ化（WebView → Kotlin移植）

- 最終目標である「Android AIBOXの車載ディスプレイで動かす」を実現する段階。
- `js/core/`配下（`smartLane.js`・`arrivalJudge.js`・`voiceDecision.js`・`formatNavigation.js`等）は依存ゼロの純粋関数として作ってあるため、**同じロジックをKotlinへそのまま書き写せる設計**になっている（この設計方針はPhase 1から継続）。
- **必要なもの**：Android Studio、Kotlin開発環境（現状Windows PCのみ・Mac不要）、実機AIBOX（購入前に「Androidバージョン」「GPS内蔵の有無」「RAM容量」の確認が必要、`HANDOFF.md`参照）。
- **費用**：AIBOX本体の購入費用のみ（開発ツール自体は無料）。Google Play経由の配布はしない（自分専用のため）想定なら、Google Play Console登録費（$25、買い切り）も不要。
- **制限**：WebViewでMapbox GL JSをそのまま動かす場合、AIBOXの性能（GPU・RAM）次第で3D表示が重くなる可能性がある。3D ON/OFFトグルは既にPhase 1から実装済みなので、性能対策として活用できる。
- **プライバシー**：影響なし（アーキテクチャ変更のみ）。

## 6. 判断の優先順位（案）

実車での走行確認（`docs/05_Phase2A実走確認チェックリスト.md`）を終えてから、以下の順で検討することを推奨する。

1. **2-1 ハイウェイモード**・**2-3 お気に入り/履歴/経由地**（追加APIなし・費用¥0・実装リスクも低いため着手しやすい）
2. **2-2 渋滞情報**（費用発生の可能性があるため、料金確認を先に行う）
3. **3-3 天気連携**（無料枠での実現性を再確認してから）
4. **3-1 オフライン対応・3-2 音声合成の再調査・4-1 オービス情報**（いずれも要調査事項が多いため、優先度は低め）
5. **Phase 3 ネイティブ化**（AIBOX実機を用意してから着手）

**繰り返しになるが、上記はすべて設計・アイデアの段階であり、何も実装・登録していません。** 着手する際は、この段階で改めてユーザーの承認を得てから進めること。
